# Day 2 — 같이 만들며 부딪히기

> 오늘의 목표: **같은 코드를 여러 명이 건드릴 때 생기는 마찰을 직접 겪고, 직접 푼다.**
> 오늘은 충돌이 나야 성공입니다. 충돌은 사고가 아니라 오늘의 교재입니다.

오늘 익히는 것: merge conflict 해결, 교차 코드 리뷰, 그리고 **의견 차이를 글로 정렬하는 법**.

---

## 09:30 · 소조 편성과 오늘의 프레이밍 (20분, 다 같이)

- 소조는 **비전공 3명이 각각 다른 조**에 가도록 섞습니다. 예: (비전공A + 가이드1), (비전공B + 가이드2), (비전공C + 아무나) — 또는 3명이 한 조로 뭉치고 가이드 2명이 리뷰어로 돕는 구성도 좋습니다.
- 조마다 **하나의 작은 공동 프로토타입**을 정합니다. 조건: *여러 명이 동시에 손댈 부분이 있을 것.*
  - 예: 화면 하나짜리 웹 앱인데 각자 섹션을 하나씩 맡기 / 여러 명령을 가진 CLI인데 각자 명령을 하나씩 맡기 / 여러 페이지짜리 소개 사이트
- **오늘의 프레이밍(중요)**: 진행자가 이 말을 꼭 해주세요.
  > "오늘 merge conflict를 내는 사람이 팀에 가장 크게 기여하는 겁니다. 우리가 실제 프로젝트에서 겪을 일을 지금 안전하게 미리 겪는 거예요."

---

## 10:00 · 공동 작업 시작 — 그리고 일부러 부딪히기 (120분)

### 1) 공동 뼈대를 먼저 만듭니다 (조당 1명이 대표로)

```
우리 조는 [만들 것]을 함께 만들 거야. sandbox/team-<조이름>/ 폴더에
아주 기본적인 뼈대만 만들어줘. 그리고 README.md에 각자 맡을 부분을
표로 정리해줘. 나머지는 각자 채울 거니까 비워둬.
```

이 뼈대를 main에 머지해서 **모두가 같은 출발점**을 갖게 합니다.

### 2) 각자 브랜치를 파고 자기 몫을 만듭니다

여기서 **의도적으로 겹치게** 배치합니다. 진행자가 이렇게 설계하세요.

- 각자 자기 파일을 만들되, **`README.md`의 담당 표는 모두가 자기 줄을 수정**하게 합니다.
- 또는 공통 설정 파일(예: 메뉴 목록, 색상 정의) 한 곳을 **모두가 자기 항목을 추가**하게 합니다.

이러면 두 번째로 머지하는 사람부터 반드시 conflict가 납니다. 의도된 겁니다.

### 3) 충돌이 나면 — 오늘의 하이라이트

```
push하려니까 이런 메시지가 나왔어: [메시지 전체 붙여넣기]

나는 merge conflict가 처음이야. 지금 무슨 상황인지 그림 그리듯이 먼저 설명해줘.
그 다음에 어떤 선택지가 있는지 알려주고, 한 단계씩 같이 해결하자.
파일을 마음대로 고치지 말고, 어느 쪽 내용을 남길지는 나한테 물어봐줘.
```

**중요**: 충돌 해결은 기술 문제가 아니라 **커뮤니케이션 문제**입니다.
"어느 쪽을 남길까?"가 애매하면 혼자 정하지 말고 상대에게 물어보세요. 그게 정답 동작입니다.

## 13:30 · 교차 코드 리뷰 (90분)

실제 프로젝트에서 쓸 리뷰 방식을 그대로 예행연습합니다.

### 1) 리뷰어를 지정합니다

- **작성자는 자기 PR을 승인할 수 없습니다.** 오늘부터 이 규칙을 지킵니다.
- 비전공 팀원도 **반드시 리뷰어를 한 번은 맡습니다.** "나는 코드를 모르는데요"가 정확히 오늘 깨야 할 벽입니다.

### 2) 로컬에서 에이전트 리뷰를 돌립니다

```bash
gh pr checkout <PR번호>      # 남의 PR을 내 컴퓨터로 가져오기
```

그 다음 자기 Claude Code 세션에서:

```
/code-review <PR번호>
```

> 이 방식을 쓰는 이유: **리뷰 모델이 리뷰어의 모델**이라 사람마다 다른 시각이 섞이고,
> 각자 기존 플랜 안에서 돌아가서 **추가 비용이 0원**입니다. 본 프로젝트에서도 이대로 갑니다.

### 3) 에이전트 리뷰를 그대로 붙여넣지 마세요 ← 오늘의 핵심

에이전트가 지적한 것 중 **내가 이해했고 실제로 중요하다고 판단한 것만** 코멘트로 남깁니다.

```
방금 리뷰 결과에서 이 지적이 무슨 뜻인지 설명해줘: [붙여넣기]
이게 이 PR에서 실제로 문제가 될 만한 건지, 아니면 사소한 건지 판단을 도와줘.
```

그리고 **에이전트가 못 보는 것**을 사람으로서 한 개 이상 코멘트합니다.

- 이거 우리가 만들려던 게 맞나요? (의도 정합성)
- 이 부분 나중에 우리가 이해할 수 있을까요? (가독성)
- 이렇게까지 복잡하게 만들 필요가 있었나요? (과설계)

### 4) 리뷰를 받고 반영합니다

```
내 PR에 이런 리뷰 코멘트가 달렸어: [붙여넣기]
이 지적이 타당한지 먼저 같이 판단해줘. 타당하면 고치고,
동의하지 않는다면 내가 왜 그렇게 했는지 설명하는 답글 초안을 잡아줘.
```

> **동의하지 않아도 됩니다.** 반박하는 것도 훌륭한 결과입니다. 단, 근거를 글로 쓰세요.

---

## 16:00 · 이견을 글로 정렬하기 (45분)

오늘 나온 의견 차이 중 하나를 골라 **이슈에 정리**합니다. 조당 최소 하나.

```
오늘 우리 조에서 [무엇]을 두고 의견이 갈렸어. A안은 [...], B안은 [...] 였어.
이걸 GitHub 이슈로 정리하고 싶어. 양쪽 주장과 장단점을 공평하게 정리하고,
어떤 기준으로 결정하면 좋을지 제안해줘. 결론은 내가 팀이랑 정할게.
```

이걸 왜 하냐면 — 에이전트가 낀 팀 작업에서는 **말로 한 결정은 다음 세션에 사라집니다.**
글로 남긴 결정만 팀과 에이전트 모두에게 전달됩니다.

---

## 오늘의 통과 기준 (게이트 B)

- 각자 머지된 PR이 최소 1개 더 있다
- **merge conflict를 직접 해결한 사람이 세 명 모두** 있다
- 남의 PR에 리뷰 코멘트를 남겨봤다 (에이전트 출력 복붙이 아니라 자기 판단이 섞인 것)
- 조당 의견 차이가 정리된 이슈가 1개 이상 있다

conflict를 아무도 못 겪었다면 **일부러라도 만들어서** 겪고 가세요. Day 3에서는 기회가 없습니다.

[진도 이슈](../../issues)에서 Day 2 체크박스를 체크하세요.

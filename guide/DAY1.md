# Day 1 — 혼자 끝까지 만들어보기

[← 진도판으로](https://flyai-kfc.github.io/fly-ai-playground/)

> 오늘의 목표: **"내가 에이전트랑 뭔가를 처음부터 끝까지 만들어서 올렸다."**
> 크기는 상관없습니다. 완성해서 남에게 보여줬다는 경험이 전부입니다.

오늘 익히는 것: Git 첫 왕복(브랜치 → 커밋 → push → PR → 머지), 그리고 "막연한 부탁" 대신 **스펙부터 잡는 리듬**.

---

## 09:30 · 오리엔테이션 (30분, 다 같이)

가이드 담당이 진행합니다. 딱 세 가지만 다룹니다.

1. **Git 흐름 한 장** — `clone`(내 컴퓨터로 복사) → `branch`(내 작업 공간 분리) → `commit`(저장) → `push`(올리기) → `PR`(합쳐달라고 요청) → `merge`(합쳐짐). 지금은 이 단어 여섯 개의 순서만 외우면 됩니다.
2. **오늘의 마인드셋** — *완벽히 이해하고 시작하지 마세요. 에이전트에게 물어보며 시작하세요.* 모르는 게 정상입니다.
3. **막힘 규칙** — 30분 넘게 막히면 무조건 팀 채널에 화면을 그대로 붙입니다. 혼자 오래 헤매는 게 유일한 실패입니다.

---

## 10:00 · 만들 것 정하고 스펙 잡기 (60분, 각자)

### 1) 뭘 만들지 고릅니다

**"하루면 끝나는 크기"**가 절대 기준입니다. 크게 잡으면 오늘 완성 경험을 놓칩니다.

아이디어가 떠오르지 않으면 아래에서 고르세요.

| 유형 | 예시 |
|---|---|
| 개인 도구 | 할 일 목록 CLI, 가계부 기록기, 파일 이름 일괄 정리 스크립트 |
| 웹 한 장 | 팀 소개 페이지, 뽀모도로 타이머, 점심 메뉴 랜덤 뽑기 |
| 데이터 | CSV 정리·요약 스크립트, 간단한 차트 생성기 |
| 자동화 | 매일 특정 정보를 요약해 파일로 남기는 스크립트 |

> 고민되면 **자기가 실제로 불편했던 것**을 고르세요. 동기가 유지됩니다.

### 2) 에이전트에게 인터뷰를 시킵니다 ← 오늘의 핵심

바로 "만들어줘"라고 하지 마세요. 이렇게 시작합니다.

```
나는 개발이 처음이야. [만들고 싶은 것 한 줄]을 만들어보려고 해.

바로 코드를 짜지 말고, AskUserQuestion 도구로 나를 먼저 인터뷰해줘.
무엇을 만들지, 누가 쓸지, 꼭 필요한 기능과 굳이 필요 없는 기능,
그리고 내가 미처 생각 못한 부분을 물어봐줘.
선택지를 줄 때는 각각이 뭘 의미하는지 쉽게 설명해줘.

인터뷰가 끝나면 sandbox/<내이름>/SPEC.md 에 스펙을 정리해줘.
그 다음 어떤 순서로 만들면 될지 계획도 알려줘. 아직 구현은 하지 마.
```

### 3) 스펙을 직접 읽고 고칩니다

나온 `SPEC.md`를 **직접 읽으세요.** 이해 안 되는 문장이 있으면 그대로 두지 말고 물어보세요.

```
SPEC.md에서 이 부분이 무슨 뜻인지 모르겠어: "[붙여넣기]"
비유를 들어서 쉽게 설명해주고, 내가 원하는 게 맞는지 확인해줘.
```

> **왜 이걸 먼저 하나요?** 에이전트는 애매한 지시를 받으면 그럴듯하게 추측합니다.
> 스펙을 먼저 글로 못 박으면 결과물이 내 머릿속과 어긋날 일이 크게 줄어듭니다.
> 이게 "에이전트 친화적 사고"의 첫 단추입니다.

---

## 11:00 · 첫 Git 왕복 (30분, 각자)

구현 전에 **스펙만 먼저 올려봅니다.** 코드가 아직 없을 때 Git을 연습하는 게 훨씬 덜 무섭습니다.

```
이제 Git을 쓸 차례야. 나는 Git이 처음이니까 한 번에 한 단계씩,
각 명령이 무슨 뜻인지 한 줄씩 설명하면서 알려줘.
내가 명령을 실행하면 결과를 붙여넣을 테니 다음 단계를 알려줘.

목표: sandbox/<내이름>-<주제> 라는 브랜치를 만들고,
방금 쓴 SPEC.md를 커밋해서 GitHub에 push하는 것까지.
```

성공했다면 GitHub 웹에서 자기 브랜치가 보일 겁니다. **여기까지 왔으면 오늘의 절반은 끝났습니다.**

---

## 11:30 · 구현 (오후 내내, 각자)

한 번에 다 만들지 말고 **작은 단위로 쪼개서** 시킵니다.

```
SPEC.md의 계획 중 1단계만 구현해줘. 다 만들지 말고 1단계만.
구현한 다음에는 내가 직접 실행해서 확인할 수 있게 실행 방법을 알려줘.
```

각 단계마다 **직접 실행해서 눈으로 확인**하고, 되면 커밋합니다.

```
방금 확인했어, 잘 동작해. 이 변경사항을 커밋해줘.
커밋 메시지는 우리 규칙(feat:, fix: 같은 형식)에 맞춰줘.
```

막혔을 때 쓰는 프롬프트:

```
이런 에러가 났어: [에러 전체 붙여넣기]
왜 이런 일이 생겼는지 먼저 한국어로 설명해주고, 그 다음에 고쳐줘.
```

> **팁**: 에이전트가 만든 코드 중 이해 안 되는 부분이 있으면 그냥 넘어가지 말고
> "이 파일이 무슨 일을 하는지 한 줄씩 설명해줘"라고 물어보세요.
> 내일 리뷰 시간에 "이거 왜 이렇게 했어요?"라는 질문을 받게 됩니다.

---

## 16:30 · PR 올리기 (30분, 각자)

```
이제 작업이 끝났어. PR을 올리고 싶어.
PR 템플릿(.github/PULL_REQUEST_TEMPLATE.md)의 항목을 채울 수 있게
나한테 하나씩 물어봐줘. 특히 "왜 이렇게 했나요"랑
"에이전트와 일하며 배운 것"은 내 말로 쓰고 싶으니까 초안만 잡아줘.
```

PR 본문의 **"에이전트와 일하며 배운 것" 3줄이 오늘의 진짜 산출물**입니다. 성의껏 쓰세요.

---

## 17:00 · 서로 머지해주기 (30분, 다 같이)

- **자기 PR은 자기가 머지하지 않습니다.** 옆 사람 PR을 열어보고 머지해 줍니다.
- 머지하기 전에 PR 본문을 읽고, 궁금한 걸 코멘트로 하나만 물어보세요. 짧아도 됩니다.
- 이것만으로 "남의 작업을 확인하고 합친다"는 감각이 생깁니다.

---

## 오늘의 통과 기준 (게이트 A)

세 명 모두 아래를 만족하면 Day 2로 넘어갑니다.

- 머지된 PR이 1개 있다
- 직접 실행해서 동작을 확인한 결과물이 있다
- PR 본문에 "왜"와 "배운 것"이 자기 말로 적혀 있다

하나라도 미달이면 **Day 2 오전을 보강 시간으로 씁니다.** 뒤처진 게 아니라, 여기가 토대라서 그렇습니다.

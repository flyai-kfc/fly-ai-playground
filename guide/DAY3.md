# Day 3 — 에이전트가 일할 환경을 직접 만들기

[← 진도판으로](https://flyai-kfc.github.io/fly-ai-playground/)

> 오늘의 목표: **에이전트를 "쓰는 사람"에서 에이전트 환경을 "설계하는 사람"으로.**
> 오늘 하는 일이 이 3일 중 실무에 가장 오래 남습니다.

오늘 익히는 것: 하네스 엔지니어링 — 에이전트의 결과 품질은 **모델이 아니라 환경**이 결정한다는 감각.

---

## 09:30 · 하네스가 뭔지 5분 만에 (다 같이)

에이전트에게 일을 잘 시키는 방법은 프롬프트를 잘 쓰는 게 전부가 아닙니다. 실제로는 세 가지가 결과를 좌우합니다.

| 축 | 뜻 | 우리 레포에서의 실체 |
|---|---|---|
| **컨텍스트** | 에이전트가 매번 읽는 배경 지식 | `CLAUDE.md` |
| **도구** | 반복 작업을 정형화한 절차 | `.claude/skills/` |
| **검증** | 에이전트가 스스로 맞는지 확인할 수단 | 테스트, 린트, 직접 실행 |

지난 이틀 동안 에이전트가 **같은 실수를 반복**한 적이 있었을 겁니다. 오늘은 그걸 프롬프트로 매번 고치는 대신, **환경을 고쳐서 아예 안 나게** 만듭니다.

---

## 10:00 · 과제 A — CLAUDE.md 규칙 한 줄 (전원 필수, 60분)

이게 오늘의 핵심 실습입니다. 반드시 **전/후를 비교**하세요.

### 1) 반복된 실수를 하나 고릅니다

지난 이틀을 떠올려 보세요.

- 커밋 메시지를 매번 우리 규칙과 다르게 썼다
- 물어보지도 않고 파일을 여러 개 한꺼번에 고쳤다
- 설명 없이 코드만 툭 내놨다
- 내 폴더 밖 파일을 건드렸다

### 2) 규칙을 넣기 **전에** 재현합니다

```
[그 실수를 유발하는 작업]을 시켜볼게. 지금 상태에서 어떻게 하는지 보고 싶어.
```

결과를 메모해 둡니다. 이게 "전"입니다.

### 3) `CLAUDE.md`에 한 줄 추가합니다

```
CLAUDE.md에 규칙을 추가하고 싶어. 문제는 이거야: [반복된 실수].
이걸 막을 규칙을 한 줄로 제안해줘. 단, 짧고 구체적이어야 해.
CLAUDE.md는 매 세션 읽히는 고정 비용이라, 길어지면 오히려 무시되니까
"이 줄이 없으면 에이전트가 실수할까?"를 기준으로 판단해줘.
```

### 4) 새 세션에서 다시 시켜봅니다 ← 반드시

**`/clear`를 하거나 새 세션을 열고** 같은 작업을 다시 시킵니다. 행동이 바뀌었나요?

> 이 순간이 오늘의 전부입니다. 내가 쓴 한 줄이 에이전트의 행동을 바꾸는 걸 직접 보는 것 —
> 그게 하네스 엔지니어링을 "이해했다"의 정의입니다.

### 5) PR로 올리고 관찰 결과를 씁니다

PR 본문에 이렇게 적으세요.

```
추가한 규칙: [한 줄]
규칙 전: [에이전트가 이렇게 했음]
규칙 후: [이렇게 바뀜]
```

## 11:30 · 과제 B — 팀 공용 스킬 하나 (전원 필수, 90분)

스킬은 코드가 아닙니다. **"이 일은 이런 순서로 하는 거야"를 글로 적어둔 파일**입니다.
그래서 비개발자가 오히려 더 잘 만듭니다 — 절차를 아는 사람이 쓰는 거니까요.

### 만들 만한 것

- `새-프로젝트-시작` — sandbox에 새 폴더 만들고 SPEC부터 잡는 절차
- `PR-올리기` — 커밋 정리 → 템플릿 채우기 → 리뷰어 지정까지의 절차
- `막혔을때` — 에러를 만났을 때 정보를 모으고 질문을 정리하는 절차
- 자기가 지난 이틀 동안 **세 번 이상 반복한 아무 작업**

### 프롬프트

```
`.claude/skills/` 에 팀 공용 스킬을 하나 만들고 싶어.
주제는 [무엇]이야. 나는 이 작업을 이런 순서로 해왔어:
1. [...] 2. [...] 3. [...]

이걸 스킬 파일로 만들어줘. 다른 팀원이 이 스킬을 불렀을 때
나만큼 잘 할 수 있게, 애매한 부분은 나한테 물어보면서 채워줘.
```

만든 뒤 **다른 팀원에게 써보게 하세요.** 안 통하면 그게 피드백입니다.

## 14:00 · 과제 C — 검증 루프 맛보기 (선택, 60분)

여유 있는 사람만. 둘 중 하나를 해봅니다.

**C-1. 서브에이전트 써보기**

```
서브에이전트를 하나 써서 우리 레포의 sandbox/ 폴더 전체를 훑고,
각 사람이 뭘 만들었는지 한 줄씩 요약해줘.
파일 내용을 전부 이 대화에 가져오지는 말고 요약만 보고해줘.
```

→ 컨텍스트를 아끼는 법을 체감합니다.

**C-2. 자가 검증 루프 만들기**

```
내 프로토타입에 아주 간단한 테스트를 하나 붙이고 싶어.
그리고 테스트를 실행하는 명령을 CLAUDE.md에 적어줘.
그 다음, 일부러 코드를 망가뜨려서 테스트가 실패하는 걸 보여주고,
네가 그 실패를 보고 스스로 고치는 과정을 보여줘.
```

→ "에이전트가 스스로 확인하고 고치는" 루프가 왜 중요한지 눈으로 봅니다.

## 16:30 · 본 프로젝트로 이관 (60분)

- 오늘 만든 스킬·`CLAUDE.md` 규칙 중 **실전에서도 쓸 것**을 골라 본 프로덕션 레포로 옮깁니다.
- 각자 본 프로젝트에서 **처음 맡을 작은 이슈 하나**를 정합니다. 오늘 겪은 흐름 그대로 진행하면 됩니다.
- 연습 레포는 남겨둡니다. 앞으로도 새 팀원이 오면 여기서 3일을 돌리면 됩니다.

## 오늘의 통과 기준 (게이트 C)

- 각자 `CLAUDE.md` 규칙 개선 PR 1개 — **전/후 관찰이 본문에 적혀 있을 것**
- 각자 스킬 1개 커밋
- 회고 작성 완료
- 본 프로젝트에서 맡을 첫 이슈가 각자 정해짐

---

## 3일이 끝나고 — 이걸 할 수 있으면 성공입니다

- 남의 도움 없이 브랜치를 파고 PR을 올려 머지한다. conflict를 한 번은 직접 풀어봤다.
- "만들어줘" 대신 스펙 → 작은 단위 구현 → 실행 검증의 리듬으로 시킨다.
- `CLAUDE.md`나 스킬을 직접 건드려 에이전트 행동을 바꿔봤다.
- 결정과 이견을 PR·이슈·문서에 글로 남긴다.
- 그리고 무엇보다 — **에이전트로 개발하는 게 더 이상 낯설지 않다.**
